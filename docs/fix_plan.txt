3. HOTFIX-01 — FIRESTORE RULES COMPATIBILITY & WALLET SECURITY

3.1. Vấn đề hiện tại

FirebaseWalletRepository hiện đã bổ sung:

status
archivedAt

vào Wallet schema.

Nhưng firestore.rules vẫn chỉ whitelist:

name
type
balance
color
isDefault
createdAt

Điều này có thể khiến Firebase production từ chối:

Create Wallet
Edit Wallet
Archive Wallet

với:

PERMISSION_DENIED

3.2. Root Cause

Application schema và Firestore Security Rules không được cập nhật đồng bộ.

3.3. File cần xử lý

firestore.rules

app/src/main/java/com/finlux/app/data/remote/firebase/
    FirebaseWalletRepository.kt

app/src/main/java/com/finlux/app/domain/model/
    FinanceModels.kt

Bổ sung Firebase Emulator Rules tests.

3.4. Yêu cầu sửa schema Rules

Wallet cần whitelist tối thiểu:

name
type
balance
color
isDefault
status
archivedAt
createdAt

Validate:

status in ['active', 'archived']

archivedAt:

null OR timestamp

3.5. Direct Balance Mutation

Hiện Rules vẫn cho owner update:

wallet.balance

nếu field là integer.

Điều này có nghĩa modified client/direct SDK vẫn có thể bỏ qua Ledger.

Repository chỉ update metadata là chưa đủ để bảo vệ security boundary.

3.6. Mục tiêu kiến trúc

Client
  │
  ├─ Edit Wallet Metadata
  │
  └─ Financial Command
          ↓
      Trusted Backend
          ↓
      Firestore Transaction
          ├─ Ledger
          └─ Wallet Projection

Wallet balance không phải user-editable metadata.

3.7. Phương án khuyến nghị

4. HOTFIX-02 — SALARY ROLLOVER PHẢI ATOMIC & IDEMPOTENT THỰC SỰ

4.1. Vấn đề hiện tại

Hiện flow đang gần dạng:

isRolloverProcessed()
        ↓
transferBetweenWallets()
        ↓
markRolloverProcessed()

Đây là nhiều thao tác tách rời.

4.2. Failure Scenario

isProcessed = false
        ↓
Transfer thành công
        ↓
Network error
        ↓
markRolloverProcessed FAILED
        ↓
Retry
        ↓
isProcessed = false
        ↓
Transfer lần 2

Kết quả:

Duplicate rollover
Duplicate ledger
Sai số dư

4.3. Lỗi fail-open

FirebaseSalaryCycleRepository.isRolloverProcessed() hiện có pattern:

runCatching { ... }.getOrDefault(false)

Điều này có thể biến:

PERMISSION_DENIED
Network Error
Firestore Error

thành:

false = "chưa xử lý"

Financial command phải fail-closed.

4.4. salaryRollovers Rules còn thiếu

App ghi:

users/{uid}/salaryRollovers/{cycleKey}

Firestore Rules cần explicit match + validation phù hợp.

4.5. Kiến trúc đúng

Rollover phải là một atomic command:

ExecuteSalaryRolloverCommand
        ↓
Firestore Transaction / Trusted Function
        │
        ├─ Read rollover marker
        ├─ Abort if already processed
        ├─ Read salary wallet
        ├─ Read savings wallet
        ├─ Validate wallets
        ├─ Calculate transfer amount
        ├─ Create TRANSFER_OUT
        ├─ Create TRANSFER_IN
        ├─ Update salary wallet balance
        ├─ Update savings wallet balance
        └─ Create rollover marker

Atomic:

ALL SUCCESS
OR
ALL ROLLBACK

4.6. Marker schema đề xuất

salaryRollovers/{periodKey}

cycleKey
status
amount
sourceWalletId
destinationWalletId
transferPairId
processedAt
createdAt

Status:

processed
skipped_zero_balance
pending_user_decision

4.7. Idempotency key

Nên deterministic:

salary_rollover:{uid}:{cycleKey}

hoặc dùng chính sanitized cycleKey làm document ID.

4.8. Không swallow database error

Sai:

getOrDefault(false)

Đúng:

AppResult.Success(true)
AppResult.Success(false)
AppResult.Error(...)

4.9. Runtime Caller còn thiếu

ExecuteSalaryRolloverUseCase phải được gọi thật sự trong runtime.

Ưu tiên server-side:

Cloud Scheduler
        ↓
Find due salary cycles
        ↓
Execute idempotent rollover command

Nếu chưa muốn backend scheduler:

App startup/resume
        ↓
Check previous cycle closure
        ↓
Execute idempotent command

nhưng vẫn phải đảm bảo command atomic.

4.10. ASK_EACH_CYCLE

Phải trở thành business state thật:

Cycle closed
    ↓
ASK_EACH_CYCLE
    ↓
Create pending decision
    ↓
UI Notification / Banner
    ↓
User:
  KEEP
  MOVE_TO_SAVINGS
  SKIP

4.11. Test bắt buộc

[ ] First execution transfers once
[ ] Second execution same cycle does nothing
[ ] Concurrent execution same cycle only one succeeds
[ ] Marker failure không thể xảy ra sau transfer vì cùng atomic transaction
[ ] Marker exists → no transfer
[ ] Zero balance → no transfer + processed status
[ ] Same source/destination → error
[ ] Missing wallet → error
[ ] Archived wallet → error
[ ] ASK_EACH_CYCLE → pending
[ ] KEEP_IN_WALLET → no transfer
[ ] Network failure → no partial financial state

4.12. Acceptance Criteria

[ ] Rollover transfer + marker nằm trong cùng atomic command
[ ] Retry không duplicate
[ ] Concurrent execution không duplicate
[ ] Firestore errors không bị đổi thành false
[ ] salaryRollovers có Rules
[ ] Có runtime trigger
[ ] ASK_EACH_CYCLE hoạt động
[ ] Ledger ghi nhận đầy đủ

5. HOTFIX-03 — FINANCIAL PERIOD ENGINE PHẢI ĐƯỢC TÍCH HỢP TOÀN HỆ THỐNG

5.1. Hiện trạng

FinancialPeriodResolver đã có và có test cho:

CALENDAR_MONTH
SALARY_CYCLE
Payday 28/29/30/31
FIRST_DAY
LAST_DAY
Timezone
Previous Period

Nhưng hiện mới là domain engine, chưa trở thành source of truth của toàn app.

5.2. Các phần còn dùng Calendar Month

Cần rà soát và chuyển:

BudgetRepository
BudgetViewModel
Transaction → Budget mapping
Reports
Dashboard
Cloud Functions
Budget alerts
Previous period comparison
Budget reset/lifecycle

5.3. Mục tiêu

Mọi logic period đi qua:

FinancialPeriod

không tự tính tháng riêng.

5.4. FinancialPeriod contract

data class FinancialPeriod(
    val key: String,
    val start: Instant,
    val endExclusive: Instant,
    val displayLabel: String,
    val basis: BudgetPeriodBasis
)

5.5. Period Key

Không tiếp tục chỉ dùng:

2026-08

Nên:

month:2026-08
salary:2026-08-10

Budget key:

{categoryId}:{periodKey}

Ví dụ:

food:month:2026-08
food:salary:2026-08-10

5.6. BudgetRepository cần đổi

Hiện dạng:

observeBudgets(YearMonth)

nên tiến tới:

observeBudgets(periodKey)

hoặc:

observeBudgets(FinancialPeriod)

5.7. Budget Model

Nên bổ sung/migrate:

periodKey
periodStart
periodEndExclusive
periodBasis

Có thể giữ month tạm thời cho backward compatibility.

5.8. Transaction → Budget Mapping

Đúng:

transaction.date
      ↓
FinancialPeriodResolver
      ↓
periodKey
      ↓
budget document

5.9. Reports / Dashboard

Các chỉ số:

Income
Expense
Budget progress
Remaining
Previous-period comparison

phải dùng cùng period.start và period.endExclusive.

5.10. Cloud Functions

Backend phải có financial period semantics tương đương Android.

Cần sửa:

onTransactionWrite
reconcileBudget
monthlyBudgetReset
budget alerts

Không giữ một lifecycle chỉ theo ngày 1 nếu user dùng SALARY_CYCLE.

5.11. Timezone

Phải chọn một:

Option A — VN only

financeTimeZone = Asia/Ho_Chi_Minh cố định

→ bỏ setting timezone.

Option B — Configurable

financialPreferences.financeTimeZone

→ Android và Functions cùng đọc.

Không để setting tồn tại nhưng backend bỏ qua.

5.12. Migration Strategy

Budget cũ:

food_2026-08

migrate non-destructive sang:

categoryId = food
periodKey = month:2026-08
periodBasis = CALENDAR_MONTH
periodStart = ...
periodEndExclusive = ...

6. HOTFIX-04 — REMINDER SINGLE SOURCE OF TRUTH

6.1. Vấn đề hiện tại

Hệ thống vẫn có:

Android AlarmManager

và:

Cloud Function sendReminderPush

cả hai có thể trigger notification và update nextTriggerDate.

6.2. Vì sao 60s Deduplicator chưa đủ

In-memory ConcurrentHashMap không bảo vệ:

App restart
Process killed
Device reboot
Multi-device
Cloud Function
Retry > 60 seconds

6.3. Phải chọn canonical owner

Option A — Khuyến nghị

Cloud Scheduler = Source of Truth

Cloud chịu trách nhiệm:

occurrence generation
nextTriggerDate
notification record
FCM push
idempotency

Android AlarmManager chỉ fallback/local assist và không update canonical recurrence state.

Option B

Android AlarmManager = Source of Truth

Nếu chọn thì disable/remove cloud scheduler.

Không tồn tại 2 owner.

6.4. Occurrence ID

Mỗi occurrence deterministic:

reminder:{reminderId}:{scheduledTimestamp}

6.5. Notification Document ID

Không dùng UUID cho cùng occurrence.

Nên:

notificationId = occurrenceId

Retry cùng occurrence phải ghi cùng document.

6.6. nextTriggerDate

Chỉ canonical scheduler được update.

6.7. Monthly recurrence contract

Phải thống nhất 29/30/31.

Khuyến nghị clamp ngày không tồn tại về last valid day.

6.8. Notification Privacy

Default nên:

VISIBILITY_PRIVATE

hoặc user-configurable, mặc định không hiển thị số tiền trên lockscreen.

6.9. Test bắt buộc

[ ] Same occurrence retry → 1 notification
[ ] Device restart → không duplicate
[ ] Cloud retry → không duplicate
[ ] Multi-device → 1 canonical occurrence
[ ] nextTriggerDate chỉ 1 owner update
[ ] Monthly recurrence ngày 29/30/31 đúng
[ ] Disabled reminder không trigger
[ ] Deleted reminder không trigger

6.10. Acceptance Criteria

[ ] Chỉ một scheduler là canonical owner
[ ] Persistent idempotency
[ ] Deterministic occurrence ID
[ ] Retry-safe
[ ] Multi-device safe
[ ] Recurrence semantics thống nhất
[ ] Privacy default phù hợp

Priority: P0 HIGH

7. HOTFIX-05 — PAYMENT ACTION IDEMPOTENCY

7.1. Phần đã sửa

Flow hiện đã kiểm tra transaction success trước khi mark paid.

7.2. Phần còn thiếu

Double tap/retry có thể tạo 2 expense transaction trước khi paid state được persist.

7.3. Giải pháp

Mỗi payment action có deterministic ID:

pay:{reminderId}:{occurrenceId}

7.4. Metadata / Marker

Có thể dùng:

sourceType = reminder_payment
sourceId = paymentActionId

hoặc command marker riêng.

7.5. Atomic Processing

Financial Command
        │
        ├─ check paymentActionId
        ├─ create expense if absent
        ├─ update wallet
        ├─ mark notification paid
        └─ persist payment marker

7.6. Test bắt buộc

[ ] Double tap → 1 expense
[ ] Retry receiver → 1 expense
[ ] Transaction failure → unpaid
[ ] Insufficient balance → unpaid
[ ] Success → paid
[ ] Success retry → no duplicate

7.7. Acceptance Criteria

[ ] Payment action deterministic
[ ] Retry-safe
[ ] Double tap-safe
[ ] Financial transaction và paid state consistent

Priority: P0 HIGH
